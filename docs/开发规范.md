# 开发规范

> **定位**：编码/工程规范与 Git 提交规范的**唯一权威**（单一事实源）。架构红线见 `docs/架构规范与红线.md`；模块业务铁律见 `docs/踩坑记录.md`；其他文档引用本文，禁止转抄正文。

## 1. 环境与双脚本

项目不携带任何固定绝对路径，支持多机任意目录可移植开发。环境初始化、切换与构建指令完全收敛至三个入口脚本（`init.ps1` 初始化 / `dev.ps1` 调试 / `build.ps1` 打包），**禁止手动安装依赖到全局环境**：

1. **源码调试**：运行 `.\dev.ps1 -Module <模块>`（当前仅 backend 单元：**中间件可达性前置校验** + 环境检查 + **两段式启动**——先 `-pl <模块> -am install -DskipTests` 装依赖链，再调试窗口对单模块 `spring-boot:run`；前端建立后增加 frontend 单元并行启动）。`-Module` 为**必填**的仓库内模块路径（如 `amao-boot/amao-boot-user-service`），脚本不绑定任何具体模块。脚本经 `scripts/local-env.ps1` 按优先级链解析 settings.xml（`MAVEN_SETTINGS` > `MAVEN_USER_HOME\settings.xml`（init 生成）> `MAVEN_HOME\conf\settings.xml` > 用户级 `~/.m2`）并以 `-s` 传给 mvnw（mvnw 不读 MAVEN_HOME，见踩坑通-9/通-10/通-11）。工具链与 JDK 判据取自项目根 `.env`（见环境纪律）。
2. **打包构建**：运行 `.\build.ps1 -Module <模块>`（当前仅 backend 单元：`mvn -pl <模块> -am package` + 产物体积打印，输出至 `<模块>/target`）。仅在用户明确要求打包/构建时执行。与 `dev.ps1` 共用同一套 `.env` / settings 解析（同样带 `-s`）——两处若各写一份必然漂移，`build.ps1` 在本次改造前就漏带了 `-s`，导致打包时依赖落回默认仓库。
3. **设备初始化**：运行 `.\init.ps1`（幂等，可重复执行）。**默认只读体检**——逐项判定 `docs/开发环境搭建.md` §4 的硬性条件，存在未通过项时退出码 3；执行必须显式：`-Apply` 全跑，`-Stage <Maven|Skills|Middleware|Data>` 只跑指定阶段（四阶段内容见该文档 §3.1）。退出码：0 成功 / 1 需用户动作 / 2 settings 冲突 / 3 环境不满足。中间件、种子与数据校验**只认本脚本这一个入口**，禁止在文档或会话里另写一套等价命令（两套路径必然漂移，本文 §1 环境纪律同源）。

   **脚本约定（新增或修改入口脚本时遵守）**：
   - **默认动作只读**："现在环境对不对"是最高频问题，不该有写盘 / 起容器 / 导数据的代价；要执行必须显式声明意图。
   - **流程用加法选择、不用 `-Skip*` 减法开关**：减法开关随阶段数增长成组合爆炸，且等于把"流程顺序"固化进脚本——顺序该由调用方（人或 Agent）决定，脚本只负责"每个阶段怎么做对"。
   - **判决与动作分离**：判据函数（`Test-*` / `Get-*`）放 `scripts\local-env.ps1`（跨入口共用）或对应脚本；**同一判据只能有一处实现**，Agent 复核环境应调用它，而不是另写一套等价检查（架构规范 §4.1）。
   - **体检不中断、执行即停**：体检模式逐项报告（要给出全貌），执行模式失败即停并给出修复命令与退出口。
   - **阶段间前置条件由各阶段动作前自行校验**（关键动作前置校验），并给出"先做哪一步"的指引，不做静默自动串联。

### 环境纪律

- 依赖环境永不进 git；Maven 依赖全部经根 `pom.xml` 固定版本号精确复现，禁止依赖锁定外的隐式版本。
- **工具链必须解析到用户真实安装的持久版本，禁止在 AI 沙箱终端里创建虚拟环境**——沙箱工具链的 home 指向会被轮换清理的临时 base，base 一换环境即坏死（潜伏性故障，换机器/换工具链小版本都不立刻发病，发病时早已查不到原因）。
- 工具链版本锁定 JDK 25；脚本检测版本不符提示重建。
- **环境就绪判据不能只看版本号**：必须校验依赖环境真实完整，覆盖「目录存在但缺关键可执行文件」的空壳形态；重建统一走清空重建，禁止增量修补（Maven 后端例外：依赖收敛在用户本地仓库，就绪重建走 `mvn -U dependency:resolve`，无需清空重建）。
- 暂停包装函数内部必须调用真正的交互原语（如 `Read-Host`），禁止写成调用自身（自递归只在错误分支触发，会冲掉真正的报错）。构建工具日志可能走 stderr 被终端显示为红字"失败"→ **成败只看退出码 `$LASTEXITCODE`**。
- **含中文注释的 `.ps1` 必须保存为 UTF-8 with BOM**：Windows PowerShell 5.1 将无 BOM 的 UTF-8 按 ANSI 解析，中文注释直接破坏语法；改完脚本用 `Parser::ParseFile` 做一次语法校验。
- **Windows 下执行本项目 `.ps1` 脚本统一用 PowerShell 7（`pwsh`）**，不用 Windows PowerShell 5.1 直接跑：5.1 与 7 的语法/行为存在差异（如 `LinkType`、`2>&1` 对 stderr 的处理），混用会让同一脚本在不同宿主下表现不一致。Agent 执行时须显式走 `pwsh`；商店版安装的 PowerShell 7 落在 `C:\Program Files\WindowsApps\<包名>\`（受保护目录），探测一律以 `Get-Command pwsh.exe` 为先，禁止只按 `Program Files\PowerShell\7` 硬探测（商店版会被漏判）。
  - **例外**：`mvnw.cmd` 内部固定调用 5.1 取 `$HOME` 算分发包目录，这是 Maven Wrapper 自身行为，不受本条约束；`scripts/local-env.ps1` 须保持 5.1/7 双版本语法交集（见其文件头说明）。
  - **宿主判据是「实际可执行且主版本 ≥7」**，不是「文件存在」：WindowsApps 下的 `pwsh.exe` 在商店版未安装时是 0 字节 App Execution Alias 占位符，执行后会转发到 5.1，属假阳性；故 `Test-Pwsh7` 必须实际执行回读 `$PSVersionTable.PSVersion.Major` 复核（与「环境就绪判据不能只看存在性」同源，见上条）。
- **本机私有路径走项目根 `.env`，既不进仓库也不进 Agent 记忆**：JDK 安装目录、Maven 分发包与依赖仓库落点、下载镜像等机器私有事实一律写入 `.env`（模板 `.env.example` 入库）。它是一台设备环境事实的唯一权威来源，可审计、可复现；禁止把这类路径硬编码进脚本或 pom，也禁止依赖会话侧记忆（会丢失、跨 Agent 不共享）。
- **由脚本生成、交给 Maven 解析的 XML 必须写无 BOM 的 UTF-8**：PowerShell 5.1 的 `Set-Content -Encoding UTF8` 会写 BOM，统一走 .NET `UTF8Encoding($false)`（见踩坑通-13）。
- **入口脚本新增的宿主依赖必须同步登记前置要求并做前置校验**：调试窗口宿主为 PowerShell 7（`pwsh`），缺失时脚本须在启动前明确报错并给出安装命令，不得让 `Start-Process` 抛笼统的"启动失败"（见踩坑通-14）。校验须达「可执行 + 版本复核」强度，不得只判文件存在（同上条假阳性）。

### 产物体积

- 构建环境保持最小依赖，只装构建必需项；混装无关库会使产物膨胀。
- 产物体积**不设上限、不做失败校验**（2026-09-24 移除原「后端 fat jar ≤100MB」红线）；`build.ps1` 构建后仅打印产物体积供观察。

### 测试门槛

- 代码改动发布前 `mvn test` 全绿（根目录执行，覆盖全部模块）。文档/技能专用提交可跳过，但须在提交信息中注明。
- **`mvn test` 不覆盖运行期配置**：`application.yaml`（含其 `${VAR:默认}` 占位符）**不经 Spring 上下文加载**，测试全绿不能作为"配置改动已生效"的证据。此类改动须**实际启动一次**（`.\dev.ps1 -Module <模块>`，或 `mvnw -pl <模块> spring-boot:run`）确认上下文与中间件连接正常——判据是启动日志出现 `Started ... in N 秒` 且无连接类异常（本轮 yaml 占位符改动即以此方式验证）。

## 2. 可观测与可追溯

1. **上下文可追溯日志**：所有后台任务及公共层发出的日志，统一携带 traceId（MDC，由 amao-common-tracelog 注入）+ 业务主键 userId，保证任意一行日志能定位到它属于哪个执行单元。
2. **关键动作可查**：所有对外生效的动作（写库、发消息、调用外部接口、人工敏感操作）发生时，必须打印包含具体参数摘要（目标对象、关键入参、判据数值）的详细日志。
3. **异常现场自落盘（自证式诊断设计）**：凡会"自己收敛"的判定出口——兜底恢复、冲突判决、撤销动作、连续失配、判失败/跳过——实现时必须**顺手把当时的现场上下文落盘**，不要留"下次复现时再看一眼"。
   理由：日志只能给出"结论 + 证据数值"，而**同一目标在不同现场下的差异只有现场快照能说清**；没有现场，根因判断只能靠猜，猜错方向会把资产/阈值退化当成环境异常，改到错的地方去。设计要点：
   - **只落在异常路径**：正常流程不落盘，长期运行才不会刷爆存储；一个异常点落一份现场（需要成对证据的场景按同一事件序号成对落盘）。
   - **目录与命名统一**：`diagnostics/<模块>/`，文件名含 `时间戳_单元标识_触发原因`；**禁止各模块自造目录层级**。
   - **保留策略必须封顶**：落盘是长跑功能，必须有三重上限（天数/份数/总容量），并在每次落盘时顺带清理旧产物。
   - **落盘尽力而为**：写盘失败只告警不阻断业务，且必须带 traceId 与落盘路径（路径要能直接复制去打开）。
   - **必须闭环成回归样本**：根因查清后把现场收编进测试 fixtures 并补一条锁定该判据/阈值的用例，异常才算真正关闭；否则同类退化换个模块还会再来一遍。

## 3. 通用工程约定

| 约定 | 说明 |
|------|------|
| 动作后验证生效 | 关键动作必须验证生效：提交后确认响应/状态已变更，操作后确认目标已出现，发送后确认回执 |
| 外部输入原样传递 | 用户提供的路径/参数/外部标识是唯一事实源：只允许为当前语言/API 做必要语法转义，禁止按任何模式增删改；访问失败前必须回显实际传入的完整值并与用户原文逐字符核对；语义不确定时先询问，禁止猜测后访问 |
| 后台任务禁触响应上下文 | 子线程/@Async 任务不得直接操作请求响应上下文，结果经 Result/事件/消息回流（架构规范 §1） |
| 身份识别用稳定标识 | 展示名/标题随版本、语言、截断变化不可靠；统一用进程名/ID/稳定主键匹配 |
| 行尾 / 缩进 / 编码 | 由仓库根 `.gitattributes`（管 git 入库规范化）与 `.editorconfig`（管编辑器写出的实际字节）统一：文本一律 LF（仅 `.ps1/.bat/.cmd` 保留 CRLF），二进制显式锁定。**禁止依赖本机 `core.autocrlf` 配置** |
| 语言陷阱 | 已知 Java 陷阱登记：判空/时区/Integer `-128~127` 缓存比较/BigDecimal 等值比较用 `compareTo` 不用 `equals`/MyBatis-Plus 逻辑删除 `deleted` 与数据库唯一键冲突——具体条目待真实踩坑后回填本表 |

### Java 编码约定（api / DTO / 注入 / 转换）

| 约定 | 强制要求 | 说明 |
|------|----------|------|
| `*-api` 注释补全 | 是 | 门面端口接口、DTO 必须写类级 Javadoc（职责/契约/空值与异常约定）；接口每个方法必须有 `@param`/`@return`；DTO **每个字段**必须有行内注释（业务含义 + 关联表字段） |
| DTO 一律 Lombok | 是 | `*-api` 的 DTO 使用 `@Data`（+ 需要时 `@Builder`）；**禁止手写 getter/setter/toString/equals/hashCode** |
| 构造器注入用 Lombok | 是 | 依赖注入统一 `@RequiredArgsConstructor(onConstructor = @__(@Autowired))` + `private final` 字段；禁止字段 `@Autowired`、禁止手写构造器注入样板 |
| 对象转换用 MapStruct | 是 | Model↔DTO、DTO↔DTO 转换一律 MapStruct `@Mapper(componentModel = "spring")`；**禁止**在 Service/Converter 里手写 `dto.setX(model.getX())` 逐字段拷贝；映射缺口用 `@Mapping` 显式声明。Converter 放 `*-service` 的 `.../service/converter/` |
| 跨域契约面 | 是 | 跨模块只依赖 `*-api` 门面 + DTO；禁止依赖对方 `*-service` 内部 Model/Mapper（双形态兼容，见架构规范） |

### 中间产物目录 `tmp/`

Agent 开发过程中的中间产物（调试脚本、临时输出、日志摘录、对比样例等）一律写入项目根 `tmp/`，禁止散落在仓库根、`docs/`、`src/` 等正式目录。

1. **按用途建子目录**：禁止直接丢在 `tmp/` 根下；按用途命名，如 `tmp/debug_export/`。同用途可覆盖旧产物，无需保留历史。
2. **不纳入版本库**：`tmp/` 已加入 `.gitignore`；本地内容随时可删，删除前无需备份确认。
3. **禁止正式依赖**：源码、测试、构建配置不得把 `tmp/` 当作正式资源路径依赖。

## 4. Git 提交信息规范

提交信息的目标是让后来排障、回滚或追溯版本的人，**不打开 diff 也能判断改动结果、验证状态和风险边界**。提交保持原子性：一条提交只服务一个可独立描述、独立回滚的目的；无关格式化、重构和功能改动不得混入同一提交。

### 标题（必填）

```text
<type>(<scope>): <用户可感知的结果> (vX.Y.Z)
```

- `type` 只能为 `feat`、`fix`、`perf`、`refactor`、`test`、`docs`、`build`、`chore` 之一。
- `scope` 使用稳定的模块或业务名（如 `system`、`user`、`common`、`docs`）；跨模块且无明确主责模块时可省略。
- 标题只说明一个结果，避免堆砌 ①②③、实现细节、文件名或测试清单；建议 ≤40 个中文字符，上限 65 个中文字符，过长内容下沉到正文。
- `vX.Y.Z` 仅用于已完成用户验收、按发布流程提交的版本；普通开发提交不带版本号。
- 作者名不写进 message（Git author metadata 已提供）。

### 正文（按影响强度决定）

标题后空一行。单点且含义直观的改动可无正文；多模块功能、修复、性能治理，或触及状态机、共享检测层、兼容性红线时必须使用以下字段：

```text
背景/目的: <仅当标题不足以说明原因时填写>
变更:
- <行为或机制变化，不罗列机械文件改名>
验证: <mvn test 及结果；未运行则说明原因>
验收: <验收通过 / 未验收 / 不适用>
文档: <同步范围；未同步则不写>
风险/遗留: <没有则不写>
```

- 正文写"为什么、行为如何改变、如何证实"，不重复 diff 可直接看出的逐行实现。
- **测试必须可判断**：写清命令或用例范围及结果（"mvn test，218 通过"），不写"已测试"；文档/技能专用提交写"无源码变更，测试不适用"。
- 触及状态机、共享层契约（amao-common starter）、兼容性红线时，正文必须写明保留的安全约束、已知风险或回退边界。

### 未验收检查点

未验收的诊断或协作检查点可以提交，但不是发布：使用 `chore(<scope>): <目的> [checkpoint，未验收]`，不得升级版本号，正文须说明已完成的验证和待验收项。

### 示例

```text
feat(user): 用户注册接口落地并统一 Result 包装

变更:
- 新增 /api/v1/user 注册接口，Controller → Service 分层实现
- 实体继承 BaseModel，日志携带 traceId
验证: mvn test，全绿
验收: 未验收
```

### 经文件传递提交信息（多行 / 含中文）

- 多行或含中文的 message 用 `git commit -F <file>` 传递时，该文件必须**无 BOM + LF 行尾**：BOM 会被写进提交元数据，CRLF 会把 `\r` 带进每一行。
- 生成方式：`[System.IO.File]::WriteAllText($path, $text, [System.Text.UTF8Encoding]::new($false))`，`$text` 用 LF 拼接（与踩坑 通-13 同类规则：**给外部工具读的文本一律无 BOM**；`.ps1` 自身反之必须带 BOM）。
- 该文件放 `tmp/`（不进库），提交后可留可删。

## 5. 发布流程

固定顺序：**代码调整 → 源码验证（`mvn test` 全绿）→ 用户验收 → 统一更新所有相关文档（含「最后更新 + 当前源码版本号」标记）→ Git Commit（作者批准，落 `dev`）→ 发布合并 `dev` → `master`（作者批准）→ 打包/部署（可选，用户不明说则不做）**。分支收口细则见 §7.3。

- 完整操作步骤（升版本、版本标记同步清单、`.scratch/` 清场）由 release 技能（`.agents/skills/release/SKILL.md`）承载；**Git 写操作授权红线**见 §7.1。
- **新信息先找家（防再膨胀）**：发布同步文档时，每条新信息只写入它的唯一权威位置——架构红线/例外→`docs/架构规范与红线.md`（例外须落 ADR + 登记表）；编码/工程规范→`docs/开发规范.md`；模块铁律→`docs/踩坑记录.md` 对应模块；配置字段/接口→`docs/配置与接口参考.md`；术语→`CONTEXT.md`；决策→`docs/adr/`。其他位置只留一行指针，禁止转抄正文。

## 6. 故障防回滚沉淀（三断言）

每次新功能开发或重大 Bug 修复通过用户验收后，必须立即把核心机理**一行一条**增补至 `docs/踩坑记录.md` 对应分组表格（`# 通用机制` / `# 模块与共享层`，后者编号列填模块名）：

| 列 | 内容 | 上限 |
|----|------|------|
| 编号 | `通-N` 稳定锚点（不随重排改变；停用编号留空不复用）或模块名 | — |
| 关键词 | 排查时用于 grep 的词：报错关键字 / 命令 / 类名 | 30 字 |
| 现象 | 触发条件 + 关键字报错（保留可 grep 的原文片段） | 110 字 |
| 根因 | 底层机理，一句话说透 | 120 字 |
| 铁律 | 可执行的强制规则：边界值 / 阈值 / 锁死逻辑 / 必须走的函数路径；末尾带位置指针（`模块::函数` / `路径::键`） | 150 字 |

- 单元格内不换行、不展开叙事：排查时间线、日志全文、实测时间戳、备选方案对比一律**不进文档**（归 commit message 或 `.scratch/<feature>/`）。
- 一条只装一条铁律；规则多了拆新编号（保持可 grep、可被其他文档按锚点引用）。
- 落盘前先查重（同模块是否已有同条目）；条目随铁律守护的代码失效即**删除或合并**——本清单是项目里唯一允许减员的文档，不做历史归档。

## 7. Git 分支规范

### 7.1 共识

**三条分支各司其职**（定位唯一权威，其他文档只留指针）：

| 分支 | 定位 | 允许的写操作 |
|------|------|--------------|
| `master` | **发布基线**：只接收 `dev` 的发布合并（`--no-ff`） | 禁止任何直接提交；禁止非 `dev` 来源的合入 |
| `dev` | **默认开发分支**（长期存续）：小改动直落 | 按判据表修改 + 逐次批准的提交 |
| `<type>/<YYMMDD>-<HHMM>-<描述>` | **大改动工作分支**：从 `dev` 开出，完成后合回 `dev` | 全部改动；合入 `dev` 后删除权归作者 |

**小改动判据表（决定直落 `dev` 还是开工作分支）**：

| 维度 | 直落 `dev` | 必须开工作分支 |
|------|-----------|----------------|
| 契约面 | 无 `*-api` 接口 / DTO 变更 | 触及 `*-api` 跨模块契约 |
| 共享层 | 不碰 `amao-common` starter | 改共享层，或新增跨模块共性能力 |
| 数据与配置 | 无 DDL / 配置契约新增，仅既有项取值修正 | DDL 变更、配置或接口契约变动 |
| 机制红线 | 不触状态机、调度推进、可取消等待 | 触及架构规范 §2 / §3 / §4 |
| 规模与验证 | 改动文件 ≤3，且可一次验证闭环（`mvn test` 全绿；配置类改动需实启一次） | 超出，或需多轮迭代 |
| 判定不确定 | — | **一律走工作分支**（保守侧默认），并在报告中说明依据哪一行判据 |

- **判定先于动手**：Agent 在开始改动前必须给出"走 `dev` 还是开分支"的结论及判据行；与作者判断不一致时先停下确认。
- **Git 写操作授权红线**：`commit` / `push` / `merge` / **删除分支**，**非作者本人明确确认批准，任何 Agent 一律禁止执行**。
  - **含分支内本地 commit**：不存在"未批准可先原子提交、事后再补批"的例外；**每次 `git commit` 前必须单独获得作者批准**。
  - **批准一次 commit ≠ 批准后续 commit**；**批准方案 / 拍板开放问题 ≠ 批准 Git 写操作**；用户触发发布技能，视为对该次发布 commit/push 的批准（技能内仍逐项校验）。
  - **直落 `dev` 不构成预授权**：判据表只规定"提交落哪条分支"，授权维度不变（ADR-0004）。
- **允许自动执行（准备动作，无需逐次批准）**：纯只读（`status` / `log` / `diff` / `show` 等）；开工同步（`git switch dev && git pull`，或 `git fetch` 后基于 `origin/dev` 开分支）；`git switch -c` 新建工作分支。工作区文件修改本身不视为 Git 写操作。
- **两条线的包含关系**：除发布合并提交本身，`master` 不得包含 `dev` 之外的任何提交（`git log --oneline dev..master` 只应出现 merge 提交）；若 `master` 上产生过独立提交（作者手动 hotfix），必须立刻回流 `dev`（`git switch dev && git merge master`）。
- **`dev` 尚未建立时**（一次性）：`git switch master && git pull` → `git switch -c dev` → 作者批准后 `git push -u origin dev`；远端默认分支由作者在平台侧决定，Agent 不改远端设置。
- **无例外**：含紧急修复（作者拍板不留例外；单人开发期间尤其如此）。
- 作者本人手动操作不强制约束，但尽可能遵守。

### 7.2 命名格式

```text
<type>/<YYMMDD>-<HHMM>-<简短描述>
```

示例：`fix/260916-1430-导出任务重复创建`、`feature/260917-0915-用户状态机重构`、`docs/260918-2010-分支命名规范登记`、`merge/260916-1512`。

| type | 含义 | 对应提交 type |
|------|------|--------------|
| feature | 新功能 | feat |
| fix | 缺陷修复 | fix |
| docs | 纯文档维护 | docs |
| chore | 配置/工程/杂项（脚本、依赖、规范） | chore |
| refactor | 重构（行为不变） | refactor |
| perf | 性能优化 | perf |
| test | 测试新增/调整 | test |
| merge | 多分支并行冲突处理的临时合并分支 | — |

规则：

- **日期**：`YYMMDD`（两位年 + 两位月 + 两位日），置于 type 之后、时分之前；禁止 4 位/8 位混用。
- **时分**：`HHMM`（24 小时制，本地时间，**开分支时刻**），置于日期与描述之间；`merge` 分支可省略描述（`merge/<YYMMDD>-<HHMM>`）。
- **分隔符**：type 与日期、日期与时分、时分与描述之间统一 `/`；描述内多关键词统一 `-` 连接，**弃用 `_`**。
- **描述**：中文短语优先，目标 ≤12 汉字、一眼看懂主题；禁止版本号、作者名、冗余动词前缀（"修复/新增/优化"由 type 表达）、日期以外的标点（`_`、`.`、空格）。
- **同分钟撞名**：描述后追加 `-2` / `-3` 消歧。
- **历史分支**：无 HHMM 的旧命名不追溯重命名；本格式只约束**新开**分支。

### 7.3 生命周期

**轨道 A —— 小改动直落 `dev`**

1. **开工（可自动）**：`git switch dev && git pull`。
2. **开发**：直接在工作区修改；在作者批准前**不得 commit**。
3. **验证**：`mvn test` 全绿（根目录执行）；文档/技能专用改动可跳过但须在提交信息中注明；运行期配置类改动须实际启动一次（见 §1 测试门槛）。
4. **提交（每次单独批准）**：向作者展示 `git status` / `git diff` 摘要与按 §4 拟好的完整 commit message → 作者明确批准 → 才可 `git add` + `git commit`。若需多次原子提交，**逐次**展示并批准。
5. **推送（批准后）**：`git push`（`dev` 首次推送用 `git push -u origin dev`）。

**轨道 B —— 大改动走工作分支，再合回 `dev`**

1. **开工（可自动）**：`git switch dev && git pull` → `git switch -c <type>/<YYMMDD>-<HHMM>-<描述>`。
2. **开发与提交**：同轨道 A 第 2-4 步（在分支上）。
3. **推送（批准后，可选）**：用 `git log --oneline dev..HEAD` 与 `git diff dev...HEAD` 向作者展示 → 批准后 `git push -u origin <name>`；纯本地单人推进可不推。
4. **合并前对齐 `dev`**：`git fetch` 后 `git switch <branch> && git merge dev`——冲突在**工作分支上**解决并复跑验证，`dev` 只接收已干净的合入。
5. **合入 `dev`（批准后）**：向作者展示 `git diff dev...<branch>` 与验证结果 → 批准后 `git switch dev && git merge --no-ff <branch>`；推送 `dev` 另需批准。
6. **不自动删除分支**：合并/推送后**禁止** Agent 执行 `git branch -d` / `git push origin --delete`。可在合并推送完成后**列出「已完全合入 `dev` 的本地/远端分支」提醒作者**，删除时机与是否删除由作者自行决定。

**merge 分支路径**（仅用于多分支并行收口到 `master`，或作者指示时）：

- 命名 `merge/<YYMMDD>-<HHMM>`；以**已与远端同步的 `master`** 为基新开。
- 将待收口分支（可多条）merge 进该分支并解决冲突。
- `mvn test` 全绿（+验收如适用）→ **通知作者验收** → 作者验收无误并批准后，再 `git switch master && git merge --no-ff <merge 分支>`；推送 `master` 另需批准。

**发布上线路径（`dev` → `master`）**

1. **发布前核对**：`git log --oneline master..dev` 确认待上线提交恰为本次发布范围；`mvn test` 全绿 + 作者验收通过（§5）。
2. **合并（批准后）**：`git switch master && git pull` → `git merge --no-ff dev`。
3. **推送（批准后）**：`git push origin master`。
4. **回流**：发布合并提交本身只存在于 `master` 上属正常（§7.1 包含关系允许）；除此之外若 `master` 出现了独立提交，必须 `git switch dev && git merge master` 回流。

### 7.4 违反处理

任何 Agent 未经作者批准执行 **commit（含分支内）** / push / merge / **删除分支**，或违反 §7.1 判据表（**把大改动直落 `dev`**）、**绕过 `dev` 直合 `master`**、**直接向 `master` 提交** → 立即停止后续写操作；未推送的擅自 commit 以 `git reset` 回退到提交前并向作者报告；已推送/已合并的不得擅自再改写历史，等待作者指示；须在提交信息或 issue 记录违规。
