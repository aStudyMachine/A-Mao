# ADR-0004：引入 dev 集成分支

> 状态：已接受
> 日期：2026-09-26 | 决策人：项目作者

## 背景

原分支规范（`docs/开发规范.md` §7.1）把"开工作分支"作为**一切**代码与文档改动的前置：改一行文档也要「开分支 → commit → push → 合 master → 推送 master」。单人多设备开发下，流程成本长期高于改动价值；同时 `master` 身兼"日常集成分支"与"发布基线"两职，后者被前者稀释——正式发布的里程碑淹没在日常提交里，回滚参照也变得不可靠。

关键事实：本仓库无 CI、无 hooks（无 `.github/`），分支纪律完全靠**文档 + Agent 自律**。因此规则必须给出可当场判定的边界，否则各 Agent 各自解释，规则必然被跑空。

## 决策

引入长期存续的公共开发分支 `dev`：**小改动直接落 `dev`**，**大改动从 `dev` 开工作分支再合回 `dev`**，`master` 退为**只接收 `dev` 发布合并**的发布基线。判据表、生命周期与违反处理见 `docs/开发规范.md` §7。

## 理由

- **收益**：日常小改动的流程从"开分支 → 合并"降为"在 `dev` 上改 + 逐次批准的提交"；`master` 的历史只由发布合并提交构成，版本里程碑与回滚参照恢复清晰；`dev` 作为长期分支天然承载"多设备对齐同一条开发线"。
- **代价**：新增一层分支与三条合并边（工作分支→`dev`、`dev`→`master`、`master` 独立提交回流 `dev`），理解成本上升——以 §7.1 判据表 + 每条边各配 git 命令缓解。
- **明确不放宽授权**：`dev` 改变的是"提交落在哪条分支"，不改变"谁批准"；`commit` / `push` / `merge` / 删除分支仍逐次由作者批准，**"小改动直落"不构成预授权**（最高红线「Git 写操作授权」原样保留）。
- **否掉的备选**：
  1. **`master` 退役、`dev` 作唯一主干**：最简，但失去稳定发布基线与回滚参照，且与"发布合并留痕"诉求冲突。
  2. **只按规模（如 ≤3 文件）判定小改动**：简单，但可能把小范围的共享层/契约改动放进 `dev`，与红线 3/4 的守护面脱钩，故改以红线面判据为主、规模辅判。
  3. **每次由作者当场拍板**：零误判，但每件小事都要打断，与本次改造动机相抵。

## 边界（锁死）

- `master` 只接收 `dev` 的 `--no-ff` 发布合并；**禁止任何直接提交**与非 `dev` 来源的合入。
- 除发布合并提交本身，`git log --oneline dev..master` 只应出现 merge 提交；出现独立提交必须在下一轮开工前回流 `dev`。
- 判据表任一维度落入"必须开工作分支"列（含"判定不确定"）即**不得直落 `dev`**。
- 授权边界不变：任何 `commit` / `push` / `merge` / 删除分支仍逐次经作者批准。
- `dev` 的建立与远端默认分支切换属作者动作域，Agent 不改远端平台设置。

## 回退

删除 `dev`（本地与远端）即回到"一切改动新开分支 → 合 `master`"的旧规范；须同步回退 `docs/开发规范.md` §7、`AGENTS.md` §三.8 与 `release` / `implement` / `project-conventions` 三处技能中的相应段落。回退前确认 `dev` 上无未合入 `master` 的提交（`git log --oneline master..dev`）。
