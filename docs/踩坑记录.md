- 【现象】问题表现是什么（含关键数据：报错、实测值、复现条件）。

- 【铁律】以后如何规避——**必须是可执行的强制规则**：边界值 / 阈值 / 锁死逻辑 / 必须走的函数路径，并附代码位置（`模块::函数`）。"注意""小心""加强关注"这类空话不是铁律。

落盘前先查重：同模块是否已有同条目？铁律守护的代码是否已失效/重构？

# 通用机制

## 通-1 PowerShell 调用 Maven 的 `-D` 参数被拆坏

- 【现象】`mvn install -Dmaven.repo.local=D:\dev\Maven\repository` 报 `No plugin found for prefix '.repo.local=D'`；`mvn wrapper:wrapper -Dmaven=3.9.9` 报 `Unknown lifecycle phase '.9.9'`（2026-09-22 实测，两条均 exit 1）。
- 【根因】PowerShell 解析器把 `-Dkey=value` 中的 `=` 与 `.` 切成独立 token 传给 mvn.cmd，Maven 收到的首参变成 `.repo.local=D` / `.9.9` 并被当作目标解析；cmd.exe 无此行为。
- 【铁律】PowerShell 下调用 Maven 凡带 `-D` 参数必须整体加引号：`mvn "-Dmaven=3.9.9"`、`mvn "-Dmaven.repo.local=D:\dev\Maven\repository"`；或使用 `--%` 停止解析符。

## 通-2 幻影改动：`git status` 显示 M 但 `git diff` 为空

- 【现象】`git status --porcelain` 显示 `GlobalExceptionHandler.java`、`DDL.sql` 为 ` M`，但 `git diff <file>` 无任何输出，`git diff HEAD --stat` 亦不含这两个文件。
- 【根因】编辑器改写文件触发 stat 变化，但经 core.autocrlf/`.gitattributes` 规范化后内容与索引一致，status 的 stat 缓存判定为「已修改」。
- 【铁律】判断文件是否有实质变更一律以 `git diff HEAD -- <file>` 输出为准，不以 `git status` 为准；幻影 M 文件不得 `git add`（会把行尾改写固化进提交），也不得据此认定用户改过代码。

## 通-3 空暂存陷阱：AM 状态但 `--cached` 零行

- 【现象】4 个新文件状态为 `AM`，`git diff --cached --stat` 显示 `0 insertions`，而工作区文件共 541 行；直接提交会提交出空文件。
- 【根因】文件曾以空内容被加入索引（`git add` 早于内容写入），此后真实内容只存在于工作区，索引与工作区不一致。
- 【铁律】每次 `git commit` 前必须核对 `git diff --cached --stat` 的文件数与行数符合预期；出现 `AM` + cached 零行组合时，必须先重新 `git add <文件>` 使暂存内容与工作区一致，再提交。

## 通-4 Nacos 3.x Docker 即使关鉴权仍强制 AUTH_TOKEN/IDENTITY

- 【现象】`docker run nacos/nacos-server:v3.1.1` 仅设 `MODE=standalone` + `NACOS_AUTH_ENABLE=false`，容器立即退出，日志：`env NACOS_AUTH_TOKEN must be set with Base64 String.`（exit 255）。
- 【根因】镜像内 `bin/docker-startup.sh` **无条件**校验 `NACOS_AUTH_TOKEN` / `NACOS_AUTH_IDENTITY_KEY` / `NACOS_AUTH_IDENTITY_VALUE` 非空，与 `nacos.core.auth.enabled` 开关无关；鉴权关闭只影响业务鉴权，不豁免启动脚本入参。
- 【铁律】凡以 `nacos/nacos-server` 3.x 镜像启动（含 `docker/docker-compose.yml` 的 `nacos` 服务），必须同时提供上述三项环境变量（Token 为 Base64）；禁止只写 `NACOS_AUTH_ENABLE=false` 就认为可省略密钥。开发占位值见 compose，生产须替换真密钥并开启鉴权。

## 通-5 脚本参数与 foreach 循环变量同名，被参数类型约束转换

- 【现象】`.\dev.ps1 -Check` 报 `[] 未找到版本  的工具链`：`Resolve-Toolchain` 收到的 `-UnitName` / `-ExpectedVersion` 都是空值，但单元配置表里 `Name` / `ExpectedVersion` 明明有值；不带参数直接运行 `.\dev.ps1` 同样失败。
- 【根因】脚本 `param([string[]]$Unit)` 与遍历循环 `foreach ($unit in $ActiveUnits)` 是**同一个变量**（PowerShell 变量名大小写不敏感），循环赋值时被参数的 `[string[]]` 类型约束强制转换——哈希表被转成 `String[]`，属性访问自然全为空，与配置内容无关。
- 【铁律】脚本内遍历配置数组的循环变量禁止与任何脚本参数同名（用 `$activeUnit` 等具名变量）；排查"配置有值却取不到字段"时，先打印 `$x.GetType().Name` 确认是否被参数声明的类型约束改写，再怀疑配置本身。

## 通-6 JDK 21+ 下 Mockito 必须显式以 -javaagent 挂载

- 【现象】`mvn test` 每个测试 JVM 刷出多行告警：`Mockito is currently self-attaching to enable the inline-mock-maker...`、`WARNING: A Java agent has been loaded dynamically (...byte-buddy-agent-1.17.8.jar)`、`Dynamic loading of agents will be disallowed by default in a future release`（2026-09-24 实测，JDK 25 + Spring Boot 4.0.8 / Mockito 5.20.0）。
- 【根因】JDK 21 起（JEP 451）禁止库向自身 JVM **动态** attach agent；而 Mockito 5.x 起 inline mock maker 是默认 mock maker，运行时靠 self-attach byte-buddy-agent 完成插桩，故必然触发告警，且未来 JDK 会直接拒绝该行为导致测试失效。
- 【铁律】凡含 Mockito 测试的模块，必须把 mockito-core 作为 `-javaagent` **显式**传给 surefire 的测试 JVM：`maven-dependency-plugin` 的 `properties` goal 把 jar 绝对路径写入 `${org.mockito:mockito-core:jar}`（不写死版本，避免与 BOM 漂移），surefire `argLine` 引用该属性；且**该配置只能写在模块自身 `<build><plugins>`**——实测放进根 pom `pluginManagement` 会泄漏到所有模块（含无 mockito 依赖者），属性解析不到时以字面量 `-javaagent:${...}` 启动直接崩 VM（仅因这些模块无测试、surefire 不 fork 才未暴露）。参考实现：`amao-modules/amao-module-user/amao-module-user-service/pom.xml`、`amao-modules/amao-module-system/amao-module-system-service/pom.xml`。

## 通-7 compose bind 路径搬迁后旧容器固化旧挂载源，容器 exit 127

- 【现象】`amao-mysql` 长期 `Exited (127)`，`docker compose ps` 显示 `Exited (127) 26 hours ago`，而 dockerd 日志里**同一容器 id** 连续两次启动失败：`error mounting "/mnt/d/.../A-Mao/doc/DDL.sql" to rootfs at "/docker-entrypoint-initdb.d/01-DDL.sql": ... not a directory: Are you trying to mount a directory onto a file (or vice-versa)?`（2026-09-24 01:21:04 / 21:07:58 实测）；此时 `sql/DDL.sql` 文件确实存在（10261 字节）。
- 【根因】bind 挂载源在容器**创建时**固化进 `HostConfig.Binds`，事后改 compose 文件不会回写到已有容器——`doc/DDL.sql` 迁到 `sql/DDL.sql`（commit `90617b8`）时该容器是 2 天前创建的，仍指向旧路径。挂载源缺失时 daemon 会自动把该路径建成**空目录**（残留 `/mnt/d/.../doc/DDL.sql` 空目录即事故指纹），于是 runc 在容器 init 阶段「目录挂到文件上」必然失败，进程根本没启动 → 退出码 127（不是 mysqld 业务错误，`docker_mysql-data` 卷内数据完好）。且失败发生在 init 阶段，Docker 不刷新 `StartedAt/FinishedAt`，`ps` 的 "26 hours ago" 是上一次**成功**运行结束的时间，会误导排查方向。
- 【铁律】一、compose 的 bind 挂载源路径变更后必须执行 `docker compose up -d` 触发重建（`docker/docker-compose.yml::services.mysql.volumes`）；**禁止**用 `docker start` / `docker restart` 复用旧容器（`restart: unless-stopped` 在 daemon 重启时同样只复用旧配置，容器会永久卡在 127）。二、判定容器是否待重建 = 比对容器标签 `com.docker.compose.config-hash` 与 `docker compose config --hash <service>`（实测 `21b74e42…` vs `ca47443a…` → 需重建）。三、排查已退出容器的真因必须看 `docker inspect <容器> --format '{{.State.Error}}'` 与 `{{.HostConfig.Binds}}`，不得以 `ps` 的 "Exited X ago" 为准。四、Docker 自动创建的空目录残留须删除（git 不跟踪空目录，`git status` 是干净的，别指望它提示你）。
