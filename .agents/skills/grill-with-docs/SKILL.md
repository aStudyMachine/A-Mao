# grill-with-docs（访谈与文档沉淀）

把 `grilling` 的设计树访谈与当前项目的领域文档治理组合起来。先解决决策，再判断哪些内容值得写入 `CONTEXT.md`、`docs/adr/` 或 `.agents/plan/`；不把讨论草稿直接当成项目事实。

## 工作流程

### 1. 只读准备

先读取当前项目的 `AGENTS.md`，再按其路由检查：

- `CONTEXT.md`：已有术语和 `_Avoid_` 约束；
- `docs/adr/`：相关的历史决策；
- `.agents/plan/` 或 `.scratch/<feature>/`：当前计划、spec 和 ticket；
- `docs/` 中与本主题直接相关的唯一权威文档。

确认现有术语和决策后，再开始设计树访谈。环境事实由 Agent 通过只读检查获取，不向用户索要可查事实。

### 2. 执行设计树访谈

按 `grilling` 的规则逐轮处理当前 frontier：

1. 每轮一次性询问当前可回答的问题；
2. 每个问题编号并给出推荐答案和影响；
3. 用户回答后重新计算 frontier；
4. 没有共享理解前，不写入领域文档，不修改业务文件。

### 3. 分类已确认内容

共享理解确认后，按唯一事实源分流：

- 新的项目术语、边界定义和必须避免的同义词 → `CONTEXT.md`；
- 不可逆的架构或流程选择、备选方案和后果 → `docs/adr/`；
- 尚未实施的工作步骤、验收标准和开放问题 → `.agents/plan/` 或 `.scratch/<feature>/`；
- 配置字段、接口契约、工程规范和模块铁律 → 按 `AGENTS.md` 路由到对应权威文档。

实现细节不因为出现在访谈中就自动成为术语或 ADR；先判断它是否具有跨任务复用价值和长期稳定性。

### 4. 写入前确认

向用户展示拟写入的文件、标题、变更摘要和被保留的边界。获得落盘确认后再修改 `CONTEXT.md`、ADR 或计划文档；用户只确认共享理解而未要求落盘时，保留总结，不擅自扩写正式文档。

落盘时查重并回链相关文档，避免同一决策在多个位置重复维护。若与已有 ADR 冲突，先显式报告冲突，不静默覆盖。

### 5. 收尾

报告：已确认的决策、写入位置、仍开放的问题，以及哪些内容明确没有写入。若进入实施，交给 `implement`；实施前仍须满足当前项目的分支、测试、验收和 Git 授权约束。

## 完成标准

设计树已收束并由用户确认；每条需要长期维护的信息都有唯一归属；`CONTEXT.md`、ADR、计划或 issue 中没有重复正文、未确认事实或与现有决策冲突的静默覆盖。
