# implement（受控实施流程）

实施已确认的 spec、计划或 ticket。它负责把已经明确的工作变成可验证的仓库改动，不替用户补做未决的产品或架构决策。

## 前置条件

- 目标来自用户明确请求、已批准的 `.agents/plan/`、`.scratch/<feature>/spec.md` 或具体 ticket。
- 目标、范围、验收标准或关键依赖仍有分歧时，先转入 `grilling` 或 `grill-with-docs`，不要带着假设编码。
- 开始前通读 `AGENTS.md`，再按 `project-conventions` 路由读取相关架构、开发、模块、配置和接口文档。
- 如果当前在 `main`，按项目分支规范创建工作分支；不能在 `main` 直接实施。

## 实施流程

### 1. 锁定事实源

先确认本次工作的 spec、ticket、计划和现有代码入口。记录明确不在本次范围内的事项，避免实现过程中扩大边界。若发现 spec 与代码或 ADR 不一致，暂停并报告冲突。

### 2. 小步实现

- 在已确认的接口或模块边界内实现一个可验证的小切片。
- 优先使用 `tdd`：先写能复现目标行为的失败测试，再实现最小改动，最后重构。
- 复用当前项目已有的共享层、错误处理、日志和配置约定，不在局部复制跨模块判定。
- 每个关键动作完成后验证结果；长流程不得用无界等待掩盖未完成状态。
- 定期运行受影响的单测、静态检查、类型检查或构建检查，使用项目实际存在的命令，不凭空假设统一工具链。

### 3. 同步项目文档

如果实现改变了配置、接口、术语、架构红线、模块铁律或目录结构，按 `AGENTS.md` 找唯一事实源更新。验收后的新机制或踩坑按 `knowledge-distill` 规则提交候选，避免把实现细节散落到多个文档。

### 4. 验证与审查

- 先运行受影响范围的测试或检查，修复失败后再运行项目声明的完整验证命令。
- 文档或 skill 专用改动可以跳过源码测试，但必须在结果中明确说明“无源码变更，测试不适用”。
- 实施完成后使用 `code-review`，分别检查项目规范和原始 spec/ticket 是否满足。
- 根据审查结果修正问题，再重新运行受影响的验证。

### 5. 提交准备与交付

完成后报告：变更文件、行为结果、验证命令与结果、审查结论、未验收项和风险。准备完整的 commit message，但不把准备提交等同于获得提交授权。

当前项目的 `commit`、`push`、`merge` 和删除分支都必须由作者逐次明确批准；没有对应批准时只保留工作区改动，不执行 Git 写操作。用户批准一次 commit 不代表批准后续 commit、push 或 merge。

## 完成标准

目标 spec/ticket 的验收条件全部有代码、文档或明确的“不适用”证据支撑；受影响验证与完整验证已执行或已说明原因；`code-review` 无未处理问题；工作区状态、剩余风险和提交方案已向作者报告，且没有越过 Git 授权边界。
